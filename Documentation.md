## 1. What Formwerk is

Formwerk (working title) is a Windows desktop application for beginners to build printable 3D models from basic shapes, edit them, and export 3MF/STL. It sits above Microsoft 3D Builder and below Fusion 360, with the ease of Tinkercad, but offline and with a real, editable history.

Guiding ideas that shape the code:

1. **Work directly in 3D** with handles (gizmos); dialogs only for exact numbers.
2. **Drag or type** – every value that can be dragged can be typed, and vice versa.
3. **Nothing is final until the user says so** – booleans, groups, holes and chamfers stay editable until "Flatten".
4. **Printability first** – millimetres, build plate visible, warnings for unprintable geometry.
5. **Sensible defaults** – snapping on, objects land on the floor.
6. **No runtime install** – self-contained build.

The full requirements are in [`docs/spec.md`](docs/spec.md) (German; the UI itself is English only). Each requirement has an ID (e.g. `F-LIB-01`), an acceptance criterion and a phase (P1–P4). `specifications.md` in the root is the original copy; `docs/spec.md` is the one to use.

## 4. Modules and their responsibilities

The dependency rule is strict. An arrow means "may reference":

```
Core ◄── Geometry ◄── Features ◄── Library
  ▲          ▲   ▲
  │          │   ├── Kernel   (Core + Geometry; the only place that knows ManifoldSharp)
  │          │   ├── Repair   (Geometry only)
  │          │   ├── IO       (Core + Geometry)
  │          │   └── Viewport (Core + Geometry)
  └── App references all of the above
```

Features never references Kernel: it receives an `IGeometryKernel` object. Only `App` (composition root, later) and tests create a `ManifoldKernel`.

| Project | Target | Responsibility | May depend on |
| --- | --- | --- | --- |
| `Formwerk.Core` | net10.0 | Document model, node tree, commands, undo/redo, expressions/parameters. Knows neither UI nor geometry kernel. | nothing |
| `Formwerk.Geometry` | net10.0 | Mesh type and metrics (`MeshData`), `IGeometryKernel` (booleans), `MeshStore` (imported meshes by id), `MeshPlacement` (unit scaling, placement on the plate), `MeshCombine` (several meshes into one, used by flatten), `FeatureEdges` + `EdgeSet` (sharp, boundary and wireframe edges of a mesh). | Core |
| `Formwerk.Kernel` | net10.0 | `ManifoldKernel`: `IGeometryKernel` implemented on ManifoldSharp. Converts `MeshData` ⇄ Manifold meshes, maps failures to `GeometryException`. | Core, Geometry |
| `Formwerk.Features` | net10.0 | Shape generators (primitives now; holes, patterns, chamfers, extrusion later) and the `SceneEvaluator` that turns the node tree into meshes. | Core, Geometry |

| `Formwerk.IO` | net10.0 | File formats: project file `.fwp` with meshes (`ProjectFile`, `MeshFormat`, `ProjectMigrations`), autosave (`AutosaveStore`), program settings (`UserSettings`, `UserSettingsStore`), binary STL export (`StlWriter`), OBJ export (`ObjWriter`, `ObjObject`), 3MF export (`ThreeMfWriter`) and import (`ThreeMfReader`, `ThreeMfLimits`), STL, OBJ and 3MF import (`MeshImport`, `StlReader`, `ObjReader`). | Core, Geometry |
| `Formwerk.Library` | net10.0 | Shape library, thumbnails, templates `.fwt` (empty so far). | Core, Features |

**Portability rule:** only `App`, `Viewport` and future `*.Windows` adapter projects may use Windows APIs. Everything else targets plain `net10.0` so a later Mac port only replaces UI, renderer and adapters.

**Runtime rules** (from the spec): geometry is evaluated on a background thread and is cancellable; the UI shows the last valid result until the new one is ready. Every document change is a command with `Do`/`Undo`. No network access, no code evaluation.

## 5. How the code works

### 5.1 The document is a tree of nodes (`Formwerk.Core.Model`)

`FormwerkDocument` owns one root `GroupNode`, the project `Settings` (build volume, nozzle, tolerance), and `Variables` (name → expression, evaluated in insertion order so later variables may use earlier ones). Geometry is **never stored** when it can be recomputed – the document stores parameters and operations.

Every `Node` has `Id`, `Name`, `Transform` (position, rotation as quaternion, scale), `Role` (`Solid` or `Hole`), `Color`, `Visible`, `Locked`, `Parent` and `Children`.

| Node type | Meaning |
| --- | --- |
| `PrimitiveNode` | A generator id (e.g. `cylinder`) plus parameters. Parameter values are **expression strings** (`"Wandstaerke*2"`). |
| `MeshNode` | Reference (`MeshId`) to a mesh in the `MeshStore` (imported; flattened objects later). The geometry itself is not in the node. |
| `GroupNode` | Moves children together; no geometry operation. |
| `BooleanNode` | Union / Difference / Intersection of its children; the first child is the minuend. Operands stay editable children; the operands' solid/hole flag does not matter. |
| `MergeNode` | Union of solid children minus hole children. |

Planned (spec section 6, not implemented yet): `SliceNode`, `HoleNode`, `PatternNode`, `MirrorNode`, `FeatureNode`.

`Node.ComputeHash(variables)` hashes everything that influences geometry (type, role, transform, evaluated parameters, children). Name, color, visibility and lock are excluded. The evaluator will cache results per hash so that only changed subtrees are recomputed.

Structural methods (`InsertChild`, `RemoveChild`) are `internal` on purpose: outside `Core`, a node can only be changed through commands. The one exception is `Formwerk.IO` (`InternalsVisibleTo`), which builds the tree directly when it loads a project file.

### 5.2 Every change is a command (`Formwerk.Core.Commands`)

- `IDocumentCommand` – `Name`, `Do()`, `Undo()`.
- `UndoHistory` – unlimited linear history. `Execute`, `Undo`, `Redo`, `JumpTo(index)` (history panel), `Entries`, `CurrentIndex`, `Changed` event, `Executed` event (only for new commands, not for undo, redo or jumping) and `AmendLast(command)` (executes a follow-up command and joins it to the last applied entry as a `CompositeCommand`, so one undo takes back both; throws when the history is not at its end). A command that throws in `Do()` is not recorded. Executing after an undo discards the redo branch.
- Commands in `NodeCommands.cs`: `AddNodeCommand`, `RemoveNodeCommand`, `SetTransformCommand`, `SetParameterCommand`, `SetRoleCommand`, `RenameNodeCommand`, `WrapNodesCommand` (group / merge / boolean – nodes must share one parent, the container takes the place of the first node), `UnwrapNodeCommand` (ungroup / separate; children keep their look by composing the container transform), `SetTransformsCommand` (one undo step for several nodes: multi-selection drags, drop to floor), `SetMeshCommand` (a mesh object gets another mesh id: the repaired mesh; undo gives the old one back, the append-only `MeshStore` keeps both), `SetSettingsCommand` (build volume, nozzle, tolerance as one undo step; `DocumentSettings` has `Clone/CopyFrom/SameAs`), `CompositeCommand` (several commands as one history entry: a resize changes parameters and position together).

`Model/TransformOps` moves and rotates nodes in **world** space: `MovedBy(node, startTransform, worldDelta)` and `RotatedAbout(node, startTransform, worldPivot, worldAxis, degrees)` and `LaidOnFloor(node, startTransform, worldPoint, worldNormal)` (the transform that turns the face at a point, with an outward direction, to look straight down about that point and puts the point at Z = 0, exact inside nested parents; a face that looks up is turned over about the X axis) take the parents' transforms into account, so a node inside a turned or moved group follows the handle along the world axes. They take the start transform explicitly, so they can be called on every mouse move of a drag. Exact for uniform parent scale. `FrameOf(node)` returns the node's own coordinate frame in world space (`NodeFrame`: origin, rotation, and the world length of one unit per axis, with `ToFrame`/`ToWorld`); the scale gizmo measures oriented bounding boxes in it.

`Model/ObjectSnapper` (pure, `System.Numerics` only) is the snapping math (F-SNP-02): `Snap(own, delta, freeAxes, targets, tolerance, includeBed)` compares, per axis the handle moves along, the minimum, center and maximum of the moving box (`SnapBox`, world-axis-aligned) with those of every target box and takes the closest match within the tolerance (flush edges, centers on centers). The floor (own lowest point to Z = 0) and the bed center lines (own center to X = 0 and Y = 0) are virtual targets. It returns the corrected delta, which axes snapped, and one `SnapGuide` per snapped axis (a rectangle in the plane at the snapped coordinate, spanning both objects).
- Each command calls `document.NotifyChanged()`, which increments `Revision` and raises `Changed`. The (future) evaluator uses the revision to drop stale background results.

To add a new editing action: write a command class, write a test that does `Execute`, `Undo`, `Redo` and checks the document, then call it from the UI via a view model.

### 5.3 Expressions and numeric input (`Formwerk.Core.Expressions`)

- `ExpressionParser.Evaluate(text, variables)` – a small safe parser: numbers, `+ - * / × ÷`, parentheses, variables, `min`, `max`, `round`. It never executes code, limits length and nesting depth, and returns an `EvalResult` (value or readable error) instead of throwing.
- `NumericInput.Resolve(text, current, variables)` – interprets what a user types into a field: `+10` is relative to the current value, `150%` scales the current value, `-4` is a negative absolute value, anything else is an absolute expression.

### 5.4 Meshes (`Formwerk.Geometry`)

`MeshData` is an immutable indexed triangle mesh (`Vector3[]` + `int[]`, counter-clockwise seen from outside). It provides `ComputeBounds`, `ComputeVolume`, `ComputeSurfaceArea`, `IsWatertight` (every directed edge once, its reverse once) and `Transformed(matrix)` (flips winding for mirroring). These metrics are the backbone of the geometry tests.

`MeshStore` holds the meshes of imported objects by id. Meshes never change after they were added, so the store only grows and undo/redo of adding or deleting an object needs no special handling; it is thread-safe because the evaluator reads it on a background thread. `MeshPlacement` prepares an imported mesh: `Scaled` (unit conversion), `PlaceOnPlate` (origin at the center of the bottom face, like the generated shapes) and `LargestExtent` (for the unit question).

`FaceFinder.Find(mesh, point, normal)` returns the flat face around a point (`FaceInfo`): the triangles that point the same way (within about 1.8 degrees), lie in one plane (within 0.02 mm) and are joined by edges (vertices at the same position count as one, so unwelded meshes work). It gives the center of mass (`Center`, in the middle of the material for a face with a hole), the size (`Extent`, the diagonal of its box), the direction and `Contains(point)` (on the face, not in a hole of it). The hole tool uses it to snap to the face center; a point that is not on a face of the mesh (or on the wrong side) finds nothing.

`IGeometryKernel.Boolean(operation, operands, cancellationToken)` is the only boundary to the boolean engine; no engine types may leak through it. The first operand is the minuend of a difference. Failures throw `GeometryException` (readable message) so the caller can keep the last valid result (F-BOO-05); cancellation throws `OperationCanceledException`.

### 5.4a The kernel implementation (`Formwerk.Kernel`)

`ManifoldKernel` implements the interface on ManifoldSharp (ADR 0003): it copies a `MeshData` into a Manifold `MeshGL`, runs union (`BatchBoolean`), difference or intersection (folded left to right with a `CancelToken` bound to the `CancellationToken`), checks `Status()` and converts the result back. Operands must be closed manifolds; an open mesh gives "Object 2 is not a closed, watertight solid …". The constructor flag `parallel` switches the library's process-wide parallel mode (default on; measured effect is small). Zero operands give an empty mesh, one operand is returned unchanged.

### 5.5 Shapes (`Formwerk.Features.Shapes`)

`IShapeGenerator` describes a primitive: `Id`, `DisplayName`, a list of `ParameterDefinition` (name, label, default, min, max, integer flag) and `Generate(values)`. The abstract `ShapeGenerator` validates values (readable errors like "Width must be between 0.01 and 10000.") and fills defaults. The origin of every shape is the **center of its bottom face**, so new shapes rest on the build plate. `ShapeLibrary.Find(id)` looks a generator up by `PrimitiveNode.GeneratorId`.

Implemented: `box`, `cylinder`, `sphere` (`BasicShapes.cs`) and `hemisphere`, `cone`, `frustum`, `pyramid`, `prism` (regular polygon, 3 to 64 sides), `wedge` (ramp rising to the back, +Y), `torus`, `tube`, `capsule` (`MoreShapes.cs`). All have their origin in the center of the bottom face, rest on the plate, are closed with outward triangles and are welded (shared vertices), which is required for the watertight check. Values that would make no sense are corrected quietly instead of reported, so that dragging a scale handle never shows an error: a tube wall of at least the radius leaves a small hole, a capsule shorter than it is wide becomes a sphere shape, a torus tube wider than the ring is shrunk to fit the ring. `ShapeMesh.Stump` builds cone, frustum and prism.

**Holes (`HoleGenerator`, F-HOL-02):** the cutter of a hole is a solid of revolution (`Revolve` turns an outline of (radius, height) points around the Z axis; `Profile(values)` returns the outline, which also draws the cross-section picture). Its axis is +Z, its origin lies on the drilled surface, it goes down to -`depth` and reaches 1 mm (`Overshoot`) above the surface so the cut is clean. Parameter `type` (`HoleType`): 0 cylindrical, 1 conical (`diameter` at the surface to `endDiameter` at the bottom, 0 gives a point), 2 countersink (cone from `sinkDiameter` down to `diameter` with the full angle `sinkAngle`, 90° by default; cut off at the depth if it would be deeper), 3 counterbore (`sinkDiameter` wide for `sinkDepth`, then `diameter`). A sink that is not wider than the hole gives a plain cylinder. A hole is a normal `PrimitiveNode` with `GeneratorId = "hole"` and role Hole, so it saves, loads, undoes, snaps and shows in the properties like any shape. All its sizes are `IsDetail` (no scale bindings: the origin is on the surface, not in the middle of the bottom). `ShapeLibrary.Find("hole")` finds it, `ShapeLibrary.All` (the shape menu) does not list it; `ShapeLibrary.Hole` is the typed instance.

**Scale bindings** (`IShapeGenerator.ScaleBindings`): each size parameter declares which local axes it drives (`ScaleAxes` flags). Box: `width` X, `depth` Y, `height` Z. Cylinder: `diameter` X+Y, `height` Z. Sphere: `diameter` X+Y+Z. Hemisphere: `diameter` X+Y+Z. Frustum: `bottomDiameter` and `topDiameter` both X+Y (the scale handles change them together), `height` Z. Torus: `outerDiameter` X+Y, `tubeDiameter` Z. Tube: `outerDiameter` X+Y, `height` Z; its `wall` is a **detail** (`ParameterDefinition.IsDetail`: a size in mm that sets no extent, the scale handles leave it alone and it has no binding). Changing a bound parameter by a factor changes exactly these extents by that factor (tested for every shape). The scale gizmo uses this to resize shapes through their dimensions instead of stretching them (F-SCL-05).

### 5.6 From node tree to meshes (`Formwerk.Features.Evaluation`)

`SceneEvaluator(IGeometryKernel)` has one method, `Evaluate(document, cancellationToken)`, returning an `EvaluationResult`: a flat list of `ScenePart`s (world-space `MeshData`, the owning `Source` node and a `PartKind`) plus a list of `EvaluationError`s. The UI renders the parts; the error list drives the red node markers.

`PartKind`: `Solid` (printed), `Hole` (negative object still waiting to cut something, internal), `Ghost` (hole that was applied or has nothing to cut; shown transparent, F-VIS-04).

Rules per node type (results are always in the parent's space, so transforms nest):

| Node | Result |
| --- | --- |
| `PrimitiveNode` | Generator mesh (parameters evaluated with the project variables) transformed by the node. |
| `GroupNode` | Children stay separate parts. Holes inside the group cut every solid of the **same group**; the holes remain as ghosts. A group with role Hole turns its solids into holes for the parent. (Open question Q-01.) |
| `BooleanNode` | One part: the children are the operands, first child is the minuend. Each child contributes the union of its parts; a child flagged as hole is an operand like any other (the operation decides what it does). |
| `MergeNode` | One part: union of the solid children minus the union of the hole children; the holes stay as ghosts. |
| `MeshNode` | The mesh from the `MeshStore` with the node's transform (role, group cuts and boolean operand work as for shapes). A mesh that is missing from the store is reported as an error. |
| Hidden node (`Visible = false`) | Skipped. |
| Holes at the top level | Nothing to cut; shown as ghosts. |

Caching and failure handling (F-BOO-03, F-BOO-05): primitive meshes are cached by generator and evaluated parameters, boolean and merge results by `Node.ComputeHash(variables)` plus the visibility of the descendants (visibility is not in the hash). `CacheHits` exposes the cache use for tests. If a node fails (`GeometryException`, bad expression, invalid parameter), the error is recorded and the node's last valid mesh is shown instead; everything else still evaluates. The evaluator is **not thread-safe**: use one instance per evaluation thread. The caller runs it on a background thread and keeps the previous result until the new one arrives.

### 5.7 The 3D view (`Formwerk.Viewport`)

`ViewportControl` takes a list of `ViewportItem` (node id, mesh, `Solid` or `Ghost`, ARGB color), the selected ids, the build volume (`System.Numerics.Vector3`) and a `PickCommand`. It draws the build plate (10 mm minor and 50 mm major grid, border, X red / Y green / Z blue axes), lights, and the items; ghosts are drawn last and transparent. Selected solids are tinted with the accent color.

- **Input:** left drag or right drag orbits, middle drag (or Shift + right drag) pans, wheel zooms, a left click without dragging picks. Keys: `F` frames the selection (or everything), `1` to `7` set the front, back, left, right, top, bottom and isometric views.
- **Picking:** a hit test along the mouse ray; ghosts win over solids so that holes inside a body stay selectable (F-VIS-04). The control reports a `PickRequest(nodeId or null, additive)`; Ctrl or Shift makes it additive.
- **Rectangle selection (`ViewportControl.Marquee.cs`, `MarqueeSelection`, F-SEL-01):** with the Select tool a left drag draws a rubber band (`MarqueeCommand`; the other tools and the face mode keep the left-drag orbit, right and middle drag always orbit and pan, Esc cancels, losing the mouse capture cancels). Dragged to the right it is a window (solid outline: only objects completely inside), to the left a crossing (dashed outline: everything the rectangle touches), decided by `MarqueeSelection.ModeFor`. `MarqueeSelection.Select` is pure: it projects the vertices with `OrbitCamera.Project`; a window needs every projected vertex inside, a crossing tests the drawn triangles against the rectangle (vertex inside, edge crossing, rectangle inside a triangle; triangles reaching behind the camera are skipped). Meshes above `DetailTriangleLimit` (20,000 triangles) use the 8 corners of their bounding box instead. An object made of several meshes needs all of them inside for a window and one for a crossing. Hidden surfaces are not considered (objects behind others are taken too). The control reports `MarqueeRequest(ids, additive)`; `MainViewModel.Marquee` maps every id like a click does (`SelectableFor`: operands of a boolean or merge give the outermost container, holes and parts of plain groups are selected themselves), then replaces the selection, or with Ctrl/Shift adds (never toggles off); an empty rectangle clears the selection unless it adds. The hint line (`Hint.SelectTool`) explains the gesture while the Select tool is on.
- **`MeshConverter`:** averages normals only across faces closer than 30° (crease angle), so curved surfaces look smooth and box edges stay sharp. Corners of one source vertex whose normals agree (within about 1.8°) share one output vertex: a smooth mesh needs about one vertex per source vertex instead of three per triangle, a box corner still gets one vertex per face (24 for a box).
- **`OrbitCamera`:** pure math (target, distance, yaw, pitch, Z up); testable without a window. `IsOrthographic` switches `CreateRay`, `Project` and `WorldPerPixelAt` between perspective and parallel projection (the width of the view at the target is the same in both, so switching does not jump). `State` (`CameraState`: target, distance, yaw, pitch) reads and sets all four; `PresetState` and `FramedState` give the goal of a standard view or of "frame" without moving the camera.
- **ViewCube (`ViewCube.cs`, `ViewportControl.ViewCube.cs`, F-VIS-05, F-VIS-06):** a small cube (112 px) in the top right corner of the 3D view, turning with the camera. It has its own `Viewport3D` with a perspective camera (`ViewCubeMath.CameraPosition`: looking along the main camera's direction from 3 units away, field of view 30) and 54 fields (`ViewCubeGeometry.Quads`: every face 3 x 3, strips of 0.2 along the edges, counter-clockwise from outside; `FrameOf` gives right/up of a face so the labels are not mirrored). A field belongs to a `ViewCubeRegion` (direction with components -1/0/1): 6 faces, 12 edges, 8 corners, the fields of a corner (one on each of its three faces) light up together. `ViewCubeMath.StateFor` turns a region into a `CameraState` that keeps target and distance (faces equal the presets 1-6, edges look from 45 degrees, corners isometric, computed in double). Hit test with `VisualTreeHelper` on the small view, hover highlight in the accent color, a click glides with the normal camera animation; the click is handled before `StopGlide` and only the first click of a series acts (`ViewCubeMath.IsActingClick`), so a double click (the acceptance wording) ends exactly in the chosen view instead of picking another field of the cube that is already turning. The face names come from `ViewCubeLabels` (property of the control, filled from `Strings.resx` by `MainViewModel.ViewCubeLabels`). It works in perspective and orthographic view.
- **Camera (`ViewportControl.Camera.cs`, `CameraAnimation`, F-VIS-06):** the wheel zooms to the mouse (`OrbitCamera.ZoomAt`: the target moves by `offset * (1 - factor)` in the screen plane, so the point of the plane through the target that is under the cursor stays under it; no drift at the distance limits). The `Orthographic` property (View > Orthographic, key P, `MainViewModel.IsOrthographic`, not saved with the project or the settings) swaps a `PerspectiveCamera` for an `OrthographicCamera` of the same width in both the scene and the gizmo view; picking, handles, snapping, rectangle selection and edge lines use the orbit camera math and work in both. Keys 1-7, F and the View menu glide to the goal in `CameraAnimation.DurationSeconds` (0.25 s, ease-out, the direction turns the short way round, start and end exact) driven by `CompositionTarget.Rendering`; any mouse button or wheel stops the glide at once, and a view that is already there or a view that is not laid out yet is set without a glide.
- It is an interim renderer (ADR 0004). Missing: edge lines, shadows/SSAO, GPU picking, snap points, zoom to cursor.

**Gizmo** (`ViewportControl.Gizmo.cs`, `GizmoGeometry`, `GizmoMath`, `GizmoTypes`): the active tool (`ViewportTool`: Select, Move, Rotate, Scale) decides the handles. *Move*: three axis arrows and three plane handles. *Rotate*: three rings. *Scale*: the outline of the object's oriented box with a small cube on each of the 6 faces (one axis) and each of the 8 corners (all axes together). The handles are drawn in a **second `Viewport3D` that shares the camera**, so they are always on top of the scene (even inside a body) and keep a constant size on screen (scaled with the camera distance). Every handle has an invisible, fatter copy that is the actual hit target. Hovering highlights a handle.

A drag is pure geometry in the control: the mouse ray (`OrbitCamera.CreateRay`) is intersected with the axis (`GizmoMath.ClosestParameterOnLine`), the plane (`IntersectPlane`) or the ring plane (`SignedAngleDegrees`, `Unwrap` for angles beyond 180°). The control reports the **unsnapped** movement or angle as a `GizmoDrag` to an `IGizmoTarget` (`BeginDrag`, `UpdateDrag` returning the text for the readout at the cursor, `CommitDrag`, `CancelDrag`). Alt (moves) or Shift (rotations) set `SnapSuppressed`. Esc cancels. The control knows nothing about the document; deciding what a drag does is the target's job (the view model).

**Scale handles** work with a `ScaleGizmoBox` (origin and rotation of the object's own frame plus min and max in that frame) that the view model provides, so the box is oriented like the object. The handles are rebuilt whenever the camera or the box changes, to keep their screen size; their size is capped relative to the smallest side of the object so that the hit areas of neighbouring handles never overlap on small objects. For a face handle the control measures how far the mouse moved along the face axis (`ScaleMath.FaceFactor`: new extent / old extent, twice as fast with Ctrl), for a corner handle where the mouse is on the diagonal from the fixed corner (`ScaleMath.CornerFactor`). It reports only the factor (`GizmoDrag.ScaleFactor`) and whether Ctrl is held (`FromCenter`). Dragging past the opposite side clamps instead of mirroring.

**Snap guides and pixel size:** every move drag also reports `GizmoDrag.WorldPerPixel` (`OrbitCamera.WorldPerPixelAt`: how many mm one pixel is worth at the object), so the view model can express its snap tolerance in screen pixels and it stays the same at every zoom (F-SNP-06). The `SnapGuides` property (a list of Core `SnapGuide`) is drawn as pink rectangle outlines in the overlay viewport, on top of the scene, rebuilt with the camera so that the lines keep their thickness.

**Drag preview (`ViewportControl.Preview.cs`, `PreviewMath`, ADR 0005):** `PreviewTransforms` (node id to a world delta matrix) moves the meshes the view already has with a `MatrixTransform3D` instead of rebuilding the scene for every mouse move; the edge lines of every object are a model of their own so that they move along without being rebuilt, and a scene that arrives while a preview is active is shown with the preview applied. `PreviewMath.ToMatrix3D` copies a `Matrix4x4` to a `Matrix3D` (both are row-vector matrices). Measured with the same benchmark before and after (Intel Iris Xe): dragging holds about 57 to 59 fps at 20,000 to 2,000,000 triangles (before: a rebuild of 95 ms at 100,000 and 1.1 s at 2,000,000 triangles per frame); orbiting 1,000,000 triangles 47 fps (before 24), 2,000,000 triangles 36 fps (before 9); memory at 1,000,000 triangles 0.77 GB (before 1.4 GB), at 2,000,000 1.2 GB (before 2.4 GB).
**Edge lines and display modes (`ViewportControl.Edges.cs`, `EdgeGeometry`, `EdgeColors`, `ViewportDisplayMode`, F-VIS-02/03):** `FeatureEdges.Extract` (Geometry, renderer independent) finds the edges where two faces meet at the edge angle or more (30 degrees by default, inclusive), the border of open meshes and edges shared by more than two triangles; triangles are joined by the position of their corners, so meshes without shared vertices work; `AllEdges` gives every triangle edge once for the wireframe. WPF 3D has no line primitive, so `EdgeGeometry.Build` makes each edge two crossing thin quads (the same width seen from every side). The width is about 1.6 screen pixels: it follows the camera distance and the lines are rebuilt only when the wanted width differs by more than 20 percent (`UpdateEdgeWidth` from `UpdateCamera`). Edge sets are cached per mesh instance (`ConditionalWeakTable`), the evaluator hands out the same mesh again while an object does not change. Colors (`EdgeColors`): dark lines on light objects, light lines on dark ones, a blue tint for selected objects, always light in the wireframe. Modes: `Shaded`, `ShadedWithEdges` (default), `Wireframe` (all triangle edges, surfaces at 5% opacity so that clicking still finds them), `XRay` (surfaces at 30% opacity plus edges); the material cache key contains the mode. Above 200,000 triangles in the scene no edges are drawn. The edge visual is separate from the parts, so picking ignores it.
### 5.8 The application (`Formwerk.App`)

`App.xaml.cs` is the composition root: it creates `ManifoldKernel`, `FileDialogService` and `MainViewModel`, and shows `MainWindow`. All state and logic are in view models (`ViewModels/`); `MainWindow.xaml.cs` only forwards camera requests to the viewport and single-key shortcuts (`H`, `Delete`, ignored while typing in a text box).

| Type | Responsibility |
| --- | --- |
| `MainViewModel` | Owns `FormwerkDocument`, `UndoHistory`, `SceneEvaluator`. Commands: add shape, undo, redo, delete, duplicate, group, ungroup, merge, boolean (union/difference/intersection), toggle hole, drop to floor, set tool, export STL, pick, set view, frame selection. Keeps the object list (`Nodes`), history list (`HistoryEntries`, `HistorySelectedIndex` jumps), selection (`SelectedIds`) and the properties panel in sync with the document. |
| `PropertiesViewModel` | Fields for the single selected node: name, hole flag, position, rotation (degrees, see `EulerAngles`), the shape's dimensions, boolean operation, size. Every edit is a command. |
| `FieldViewModel` | One text box: accepts numbers, expressions (`20/2+3`), relative input (`+10`), percent (`150%`) and variables; on error it keeps the typed text, shows a red border and a tooltip, and changes nothing. |
| `NodeItemViewModel` | One row of the object list (indent, glyph, visibility check box, hole and error markers). |
| `Resources/Strings.resx`, `Texts`, `LocExtension` | All UI text (English). XAML: `{res:Loc Key}`; code: `Texts.Get("Key")`. |
| `Views/TextBoxBehavior` | Enter applies the typed value, Escape discards it. |

How a change flows: a command runs on the document, which calls `NotifyChanged`; `MainViewModel` rebuilds the lists, refreshes the properties and starts an evaluation. The evaluation works on `FormwerkDocument.Snapshot()` (a deep copy with the same ids) on a background thread; a newer change cancels the older run, and the result is applied only if it is still the newest one. The viewport therefore shows the last valid result while a new one is computed.

**Gizmo drags (`MainViewModel.Gizmo.cs`, implements `IGizmoTarget`):**

- **Tools and snap settings:** `ActiveTool` (toolbar buttons and keys Q/W/E), `SnapToGrid` + `GridStep` (0.1/0.5/1/5/10 mm), `SnapAngles` + `AngleStep` (1/5/15/45/90°). They live in the status bar and are remembered between sessions (see Settings below).
- **Pivot:** `GizmoPivot` is the center of the bounding box of everything the selected objects show (solids and hole ghosts), recomputed after every evaluation, so the gizmo follows the object while it is dragged.
- **Preview:** `BeginDrag` remembers the start transforms of the selected top-level objects (refused when nothing is selected or an object is locked). Every `UpdateDrag` sets the transforms of the nodes directly (no history entry) and raises `NotifyChanged`, so the normal background evaluation shows the true result live, including booleans and holes. During a drag the object list and selection are not rebuilt.
- **Snapping:** done here because only the view model knows the objects. A handle only moves along its own axes (enforced here). **Priority per axis: other objects, then the grid.** At `BeginDrag`, `PrepareObjectSnapping` collects the bounds of the selection and of every other visible solid part (children of groups included, ghosts and the dragged objects excluded); `SnapMove` calls `ObjectSnapper` with a tolerance of `SnapTolerancePixels` (10) times `WorldPerPixel`; an axis that snapped to an object is not snapped to the grid any more, the other axes still are (`SnapToObjects` checkbox, `SnapToGrid`, Alt = no snapping at all). The guides are published as `SnapGuides` and cleared on commit and cancel. Grid snapping snaps the world position of the first selected object, only along the axes the handle moves in; the other selected objects follow by the same delta. Rotations snap the dragged angle to the step. Moves use `TransformOps.MovedBy`, rotations `TransformOps.RotatedAbout` around the pivot at the start of the drag.
- **Commit and cancel:** `CommitDrag` executes one `SetTransformsCommand` ("Move Box", "Rotate 3 objects"), or nothing if the result equals the start; `CancelDrag` restores the start transforms.
- **Scale (`MainViewModel.Scale.cs`):** works on one selected object (with several selected the hint asks to select one or group them). `ComputeScaleBox` measures the oriented box from the evaluated parts in the object's frame (`TransformOps.FrameOf`: world position, rotation and the world length of one frame unit). A drag becomes: the requested factor per axis (the dragged axis; all axes for corners and in *Proportional* mode `ScaleLinked`), snapped so that the new size is a multiple of the grid (Alt = off) and at least 0.1 mm; the fixed point per axis (the opposite side or corner, or the center with Ctrl; axes that are only scaled because of linking use the center). **Shapes** are resized through `ScaleBindings`: new parameter values (clamped to the parameter range), then the real new bounds from the generator give the exact position shift that keeps the fixed point where it was. **Groups, booleans, merges and meshes** change their `Transform.Scale` and are shifted by `fixedPoint * (1 - factor)`. The preview mutates parameters and transform directly; `CommitScale` restores the start and executes one `CompositeCommand` ("Scale Box") of `SetParameterCommand`s and a `SetTransformsCommand`, `CancelScale` restores. The readout is the new size as `B × T × H mm` with one decimal. A parameter that was a variable expression becomes a plain number when its dimension is scaled.
- **Drop to floor** (button, Edit menu, key B): for every selected object, moves it so that the lowest point of what it shows is at Z = 0 (one undo step; objects already down are skipped).
- **Keep on floor (`MainViewModel.Floor.cs`, F-FLR-01):** the check box "Keep on floor" in the status bar and the settings dialog (`UserSettings.AlwaysOnFloor`, off by default, remembered). While it is on, every new command is followed by a check of the next evaluation result: each unlocked top-level object (a group as a whole) whose lowest solid point is not at Z = 0 gets a `SetTransformsCommand` "Drop to floor" that is joined to the entry that caused it with `UndoHistory.AmendLast` (one undo takes back the turn and the correction together; it only joins when that entry is still the last applied one, otherwise it is an entry of its own). Switching the option on checks the scene at once (one entry "Drop to floor", also from the settings dialog). Objects that are only holes and locked objects stay where they are; undo, redo, opening files and the autosave recovery are not corrected (`ExpectFloorCheck` is fed by `UndoHistory.Executed` only). `FloorChanges` is shared with the Drop to Floor command. Because it applies to all top-level objects, stacking or lifting is only possible with the option off.

**Settings (`MainViewModel.Settings.cs`, `SettingsViewModel`, `Views/SettingsWindow`, F-SET-01/02, F-VIS-05):** File > Settings... (Ctrl+,) opens the dialog through `IDialogService.ShowSettings` (real window in the app, `FakeDialogs.SettingsAnswer` in tests). Two kinds of settings: *project* settings (build volume X/Y/Z, nozzle, tolerance) live in `FormwerkDocument.Settings`, are saved in the `.fwp` and change through `SetSettingsCommand` (one undo step, dirty flag, no history entry when nothing changed); *program* settings (`UserSettings`: default values for new projects, snap toggles and steps, snap distance in pixels, autosave minutes, slicer path) are remembered in `%APPDATA%\Formwerk\settings.json` by `UserSettingsStore` (atomic write; reading never fails: a missing, damaged or hand-edited file gives defaults, values are clamped by `Normalized()`). `MainViewModel` takes an optional `UserSettingsStore` (null in tests that do not care); the snap toggles of the status bar save on every change; "Also use these values for new projects" copies the project values into the defaults, and New starts with the defaults. `SettingsViewModel` holds one `FieldViewModel` per number (expressions allowed, dot as decimal separator, per-field range with an explanation), keeps OK disabled while anything is invalid and offers printer presets. `App.xaml.cs` creates the store and lets the autosave timer follow `AutosaveMinutes`. A grid or angle step from the dialog that the status bar does not list is added to its choices. The slicer path is only stored for now.
**Drag preview in the view model (`MainViewModel.Gizmo.cs`):** when a move or rotate handle is dragged and every dragged object sits directly in the scene (so it cannot change the shape of another object), `UpdateDrag` does not call `NotifyChanged` any more: `ShowDragPreview` computes for every dragged object and everything inside it the matrix `inverse(world matrix at the start) * current world matrix`, publishes it as `PreviewTransforms`, moves the handles (`GizmoPivot`) and refreshes the position fields. A group with holes inside is moved as a whole and is rigid, so it uses the preview too. Objects inside a group (holes, boolean operands) keep the live recalculation, because the cut result depends on their position; the same holds for scale drags (the shape changes) and for a drag that starts while the result of the previous drag has not arrived yet (the view would not show the objects where they are). On release the command is executed as before; the preview stays on screen until the evaluation after the release is applied (`ApplyResult` clears it, first, so that the new meshes are not moved twice); Esc clears it at once. While dragging, the red "outside the build area" tint, the status text and the mesh check do not update; they follow when the mouse is released.
**Display modes and edge angle (`MainViewModel.Display.cs`, F-VIS-03, F-SET-02):** `DisplayMode` (View > Display with four checkable items, key Z cycles through the modes; not remembered between sessions) and `EdgeAngle` (remembered through `UserSettings.EdgeAngleDegrees`, 1 to 90 degrees, field "Edge angle" in the settings dialog) are bound to the viewport.
**Outside the build area (F-VIS-05):** after every evaluation `FindOutside` compares the bounds of each solid part with the build volume (0.01 mm tolerance, so touching the border is fine; below the plate or above the height counts as outside; holes never do). Marked objects get a red tint in the viewport (`ViewportItem.Outside`), a ⚠ in the object list (`NodeItemViewModel.IsOutside`) and a note in the status bar. `BuildVolume` raises a change notification with every document change, so the plate redraws at once; the viewport also draws a faint outline of the build height.
**Themes (`Views/ThemeManager.cs`, `ViewportControl.Theme.cs`, F-VIS-07):** dark is the default, light is optional (View > Light Theme or the check box in the settings dialog; `UserSettings.LightTheme`, remembered, not part of a project). `ThemeManager.Apply` sets the Fluent `ThemeMode` of the application (standard controls, dialog frames) and gives the seven palette brushes of `App.xaml` (`WindowBrush`, `PanelBrush`, `PanelBorderBrush`, `TextBrush`, `MutedTextBrush`, `AccentBrush`, `ErrorBrush`) the colors of `ThemePalette.Dark` or `ThemePalette.Light`. All XAML refers to these brushes with `DynamicResource` (a test checks that no `StaticResource` of them is left) and the manager puts new brushes under the same keys, so every open window and dialog follows at once; with `StaticResource` the panels stayed dark while the controls turned light. The accent is the program's own, not the one of Windows: the Fluent theme turns the accent color of Windows into dozens of brushes when it loads (and its `SystemAccentColor*` entries are internal references that application resources cannot override), so `ThemeManager.RecolorFluentAccent` takes every brush of the theme dictionary in the hue of the Windows accent (`AccentRecolor.IsAccent`: same hue within 14 degrees, colorful, visible) and recolors it to the hue of `ThemePalette.Accent` with the same differences in lightness (`AccentRecolor.Recolor`; the default accent fill becomes exactly the program accent, hover, pressed, text and selection shades keep their order). The new brushes shadow the theme's in the application resources and are replaced on every theme switch; `SystemAccentColor` and its six shades (`AccentShades`) are set as well for controls that read them. A test loads the real Fluent dictionaries and checks that no brush keeps the Windows hue. The palettes are checked for contrast (text 7:1, muted text and error 4.5:1, accent 3:1 on window and panel); the dark error red was lightened slightly for that. The 3D view has its own `LightTheme` property (light gradient background, light plate and grid, darker snap markers and dimension lines); the ViewCube and the dimension labels keep their dark look, which reads well on both. The window applies the theme in `App.xaml.cs` (composition root) when the view model property changes. Questions and messages (unsaved changes, crash recovery, errors) are shown in `Views/MessageWindow` in the theme of the program instead of the white Windows message box: `MessageViewModel` (testable) knows the buttons (`UnsavedChanges`: Save, Don't save, Cancel; `Question`: Yes, No; `Error`: OK), the default button, and that closing the window or Esc answers with the cancel button (Cancel, No, OK); `DialogService` maps the answer. The open and save file dialogs are the common dialogs of Windows (they follow the Windows app mode).
**Fast holes (`MeshUnion`, `SceneEvaluator.CutSolid`, F-BOO-03, Q-03):** two measures, both exact (the result always equals a calculation from scratch). (1) `MeshUnion.Compute` unites many meshes: pieces whose bounding boxes neither overlap nor touch (closer than 0.001 mm) cannot meet and are put together with `MeshCombine.Concat`; only groups of pieces that overlap or touch, also through a chain (`Partition`, a sweep along X with union-find), go to the boolean engine, one call per group. A plate with 50 separate holes needs no union at all (the engine took 600 to 700 ms for it). Used for the holes of a group and for the solids and holes of a merge. (2) While one hole is dragged, `CutSolid` remembers per group and solid the hole hashes of the last calculation (FNV-1a over the vertices and indices): when exactly one hole differs and the solid is unchanged, the second step in a row for the same hole builds the solid without all the other holes and keeps it; every further step only cuts the moved hole out of that (one boolean, no union). Any other change (another hole, a changed plate, a hole added or removed, undo) is calculated from scratch and drops the remembered solid; at most 64 remembered solids, none for solids above 300,000 triangles. Measured with a 200 x 120 x 8 plate and 50 holes of 32 segments: one move took about 900 ms before, about 300 ms with the union change, and stays under 200 ms with the incremental cut.
**Templates (`Formwerk.IO/TemplateFile.cs`, `TemplateStore.cs`, `MainViewModel.Templates.cs`, `SaveTemplateViewModel`, `Views/SaveTemplateWindow`, F-TPL-01..03):** Edit > Save as Template... (needs a selection) opens a dialog (`SaveTemplateViewModel`: name required, optional description, category and tags; a name that is already used in the category is refused and "Name (2)" is offered, one click takes it; length limits). The selected top-level objects are saved with their whole structure as one `.fwt` file in `Documents\Formwerk\Templates` (`TemplateStore`): a zip with `template.json` (name, description, category, tags, size, date), an optional `preview.png` (160 x 160, rendered offscreen by `TemplatePreviewRenderer` with the same `ViewportControl`, without the ViewCube) and `project.fwp`, the normal project format with the objects as children of the scene, so parameters, holes, groups, booleans and imported meshes are kept. The objects are normalised before saving: X and Y of the middle of the selection at 0, lowest point at Z = 0, so a template lies on the floor when inserted; the size is stored in the description so inserting needs no calculation. The left panel lists the templates ("My Templates": picture, name, category); a click calls `InsertTemplate`: one object comes back with the template name (unique), several objects as a group with that name, at a free spot on the plate (`FreeSpot`), selected, one undo step. Nothing is turned into a flat mesh, so a hole diameter in an inserted template can be changed with the geometry updating live. Template files are treated like any import: at most 8 zip entries, 64 KB description, 2 MB preview, the project inside is read with the project limits, damaged files are skipped in the list (and never deleted) and give a message when inserted. Names cannot make the file leave the folder (a safe file name plus a number). Variables of the project are stored with the template but not merged into the project on insert. (There is no way yet to create project variables in the program, F-PAR-03 is phase 2, so this only matters for hand-edited project files.) The list reads the folder again whenever the main window is activated (`RefreshTemplatesCommand`), so templates that appear or disappear while the program runs are noticed; an unchanged folder leaves the list alone (no flicker).
**Dimensions in the 3D view (`MainViewModel.Dimensions.cs`, `ViewportControl.Dimensions.cs`, `ViewportDimension`, F-PAR-02):** with exactly one unlocked shape selected, the view shows one dimension per parameter that the scale handles bind to an axis (a box: width, depth, height; a cylinder: its diameter once and its height): a line with end marks along an edge of the object's own box (so a turned object has its dimensions along its own axes) moved a little away from the object (2 % of the viewing distance, so the size on screen stays the same), and the value ("20 mm") in a small label. A click on the label opens an input box right there with the number selected; Enter reports a `DimensionEdit(id, text)` and `MainViewModel.EditDimension` types it into the matching parameter field of the panel, so expressions, `+10` and `150%`, validation, undo (one step) and evaluation are the same as there; a wrong value changes nothing and says why in the status bar; Esc or leaving the box cancels. No dimensions for nothing selected, several objects, groups, booleans, imported meshes or locked objects, and none while a handle is dragged. Shortcut keys of the view are ignored while the input box has the focus.
**Snap points and priorities (`ObjectSnapper`, `ViewportControl.Markers.cs`, F-SNP-01, F-SNP-06):** every box has 27 snap points (`ObjectSnapper.Lattice`: 8 corners, 12 edge middles, 6 face centers, the center; the box is the world bounding box, so the face centers of an upright cylinder, cone or tube are its circle centers, a turned round part gets the points of its box). Priorities while a move drag snaps to other objects: first a whole point of ONE other object (on every axis some coordinate of the moving box, min/center/max, comes within the tolerance; axes the handle cannot move must line up already; the lowest movement wins), then the alignments per axis (edges, faces, centers; floor and bed center lines), then the grid for the axes that are left. `SnapResult.Marker` carries the point; `MainViewModel.SnapMarkers` publishes it during the drag and clears it at the end or on cancel. The control draws small cubes on top of the scene (same overlay as the handles, size follows the zoom): hovering an object with the Move tool shows its 27 points (throttled to every 40 ms, a hit test each) and highlights the one within 12 px of the mouse; a snapped point is shown in yellow while dragging. Above 300,000 triangles in the scene (`HoverMarkerTriangleLimit`) the hover markers are off, because every mouse move would hit test the whole scene (about 40 ms per million triangles, measured); clicks, drags and the snapped-point marker are not affected.
**Hatched hole ghosts (`GhostHatch`, `ViewportControl`, F-VIS-04):** a ghost (a hole that was applied or has nothing to cut) is drawn see-through with diagonal stripes. The stripe coordinate is a function of the world position alone (`GhostHatch.Coordinate`: planes across the direction (1, 1, 1), 5 mm apart), so the stripes keep their width on every object and do not swim when the camera turns. WPF 3D clamps texture coordinates outside 0..1 and draws tiled brushes (`DrawingBrush`, `ImageBrush`) as nothing in this setup, so `GhostHatch.LayoutFor` maps the coordinates of one object onto 0..1 and the material is one `LinearGradientBrush` with hard-edged stops, one strong and one faint half per stripe (at most `MaxPeriods` = 120 stripes, a huge object gets wider ones). The converter's frozen geometry is cloned for ghosts to take the texture coordinates. Dimmed ghosts (outside an open group) stay plain faint. View > Show Holes (`MainViewModel.ShowHoles`) hides all ghosts; the solids are untouched and the choice survives new results.
**Open groups (`MainViewModel.OpenGroup.cs`, F-BOO-04, F-BOO-02 in the 3D view):** a double click (`ViewportControl` `OpenGroupCommand`, handled before the handles because the second click often lands on one) on a part of a group, boolean or merge opens that container (`OpenContainerId`; the part is selected; a single top-level object has nothing to open). `BuildViewportItems` marks every item outside the container `Dimmed`: drawn as a faint see-through shape, no edge lines, not taken by a selection rectangle. Inside, `SelectableFor` returns the direct part of the container (an operand of an open boolean alone, a nested group as a whole), a click on a dimmed object leaves the mode and selects that object, a click on empty space only clears the selection, a double click on empty space leaves. Esc (`MainWindow.OnKeyDown`, only when the view did not use the key) calls `ExitGroup`: one level up for nested groups, the container is selected. A document change that removes the container (undo), New and Open leave the mode. The hint line names the open group.
**OBJ export (`MainViewModel.ExportObj.cs`, `ObjWriter`, E-03):** File > Export OBJ... writes the same objects as the 3MF export (every visible solid by name, holes already subtracted, ghosts and hidden objects not exported) through `ObjWriter.SaveAtomic` (temporary file, then rename; the folder is created; `.obj` is appended when the user left it out; the write runs on a background thread). The file is plain text: UTF-8 without a byte order mark, `\n` line ends, first two lines are comments (generator, "units: millimetres, Z up"), then per object `o name` (control characters in the name become spaces, an empty name gives "Object"), its `v x y z` lines (invariant culture, at most 6 decimals, no exponent, never "-0") and `f a b c` lines with 1-based indices that continue across objects. No normals, texture coordinates or materials (colors are a 3MF feature). The command is available when there is something to export and fails with a status-bar message, never a crash.
**3MF export and "Open in Slicer" (`MainViewModel.Slicer.cs`, `ISlicerLauncher`, `Views/SlicerLauncher`, E-03):** File > Export 3MF... (Ctrl+Shift+E) writes the calculated result through `ThreeMfWriter`: every visible solid part is one 3MF object with its node name and color (`basematerials`, equal colors share one entry), in millimetres and world coordinates, holes already subtracted, ghosts and hidden objects left out. The writer streams the XML by hand (fast, 1 M triangles in well under a second), names are cleaned and escaped, numbers never use an exponent, the ZIP has fixed timestamps (same input gives the same bytes), and `SaveAtomic` keeps an existing file when saving fails. File > Open in Slicer writes `%TEMP%\Formwerk\<project name>.3mf` and starts the slicer through `ISlicerLauncher` (the real one starts a process without a shell, the file path is one argument); without a stored, existing slicer path the user is asked once for the program, and it is remembered after it started (also editable in Settings). Both commands run the write on a background thread; failures appear in the status bar (export) or in a message box (slicer cannot start).
**90 degree turns and face on floor (`MainViewModel.Orientation.cs`, `ViewportControl.FacePick.cs`, `FaceMath`, F-ROT-04):** Edit > Rotate 90° (six entries: about X, Y, Z in both directions, no shortcut) turns all selected, unlocked objects about the center of the selection (the point the handles use) with `RotatedAbout`, one `SetTransformsCommand`. Edit > Face on Floor and the toolbar button start a one-shot mode (`IsPickingFace`, the hint says what to click, Esc cancels, the cross cursor shows it); while it is on, the viewport (`FacePickMode`) does not select on a click but reports a `FacePick` (node id, hit point and outward normal in world space) through `FacePickCommand`: the nearest solid under the mouse (ghosts are ignored), the normal from the winding of the displayed triangle (`FaceMath.TriangleNormal`; a click on nothing keeps the mode on). `LayFaceOnFloor` (public, tested directly) finds the outermost object below the scene root that owns the picked part (a boolean operand or a member of a group turns with its container), ends the mode, refuses locked objects (message), says when the face already lies on the floor and otherwise executes one `SetTransformCommand` "Lay Box on a face" with `TransformOps.LaidOnFloor`; the turned object is selected. The face is the clicked triangle (exact for flat faces, a facet for curved surfaces); if other parts of the object reach below the face they stick through the plate (red tint) because the criterion asks for the face to be at Z = 0, not the lowest point.
**Copy, paste and duplicate (`MainViewModel.Clipboard.cs`, F-CPY-01):** `_lastOffset` is how far a new copy lands from its original, in world space: the offset of the last move by a move handle (`CommitDrag` reports the world movement of the first dragged object; a cancelled drag, a rotation, a scale and drop to floor do not count) or by typing a position (`PropertiesViewModel` reports the world movement through an `Action<Vector3>`), or of the last duplicate; a move by zero keeps the old value; before any move it is 15 mm along X. **Ctrl+D** (`Duplicate`) copies every selected object next to itself, converted to the parent's space by `TransformOps.MovedBy` (so the offset is the same on screen inside a turned group), adds each copy to the parent of its original and selects the copies, so that pressing the key again continues the row at the same distance (acceptance criterion: after one move by 15 mm, three presses give a row with 15 mm spacing). Copies are named "Box copy", "Box copy 2", "Box copy 3" (an existing " copy" or " copy N" suffix is not repeated). **Ctrl+C / Ctrl+V** (`Copy`, `Paste`, also in the Edit menu): the clipboard is internal to the program (no system clipboard, no cut) and holds clones of the selected objects with their children, their world matrix and the meshes they use; paste puts copies into the scene root at the old world place (a non-uniform parent scale together with rotation is approximated, like ungrouping) plus one offset, pasting again adds one more offset (a new copy starts over), all in one undo step with the pasted objects selected; the meshes are put back into the store when New or Open emptied it. The key bindings are on the window, a focused text box keeps its own Ctrl+C and Ctrl+V.
**Flatten (`MainViewModel.Flatten.cs`, F-GRP-04):** Edit > Flatten replaces every selected object that is not a mesh yet and not locked by a `MeshNode` with the same name, color and place. The command first waits for a pending evaluation, because the mesh comes from the evaluated scene: all visible solid parts of the object (so the cuts of holes and booleans are applied; hole ghosts and hidden parts are not part of it), put together with `MeshCombine.Concat`, converted from world space into the space of the object's parent (a flattened object inside a moved and turned group stays exactly where it is) and moved so that its origin is the center of its bottom, like imports. The old objects are only taken out of the tree (`RemoveNodeCommand` plus `AddNodeCommand` at the same index in one `CompositeCommand`, no new command class), so undo brings them back with every parameter and child; redo flattens again. Several selected objects are flattened one by one in one undo step; the result is selected. The new mesh gets the color of the solid parts when they all agree, else the color of the object. If nothing can be flattened (only meshes, locked objects, a lone hole, nothing visible) the status bar says so and nothing changes. A flattened object has no dimensions any more; several overlapping solids stay several closed shells in one mesh (use Merge first to unite them).
**Mesh check and repair (`MainViewModel.Repair.cs`, `RepairText`, banner in `MainWindow.xaml`, F-IMP-03, F-REP-01/02/04):** whenever the selection changes (or a repair, undo or Open changes the mesh of an object) `QueueRepairCheck` looks at the mesh objects among the selected ones, also inside selected groups. Meshes it has not seen are analysed on a background thread (`MeshAnalyzer.Analyze`; results are cached per mesh id, which is valid because a mesh never changes under its id). The banner above the 3D view says what is wrong ("Bad has mesh problems: 1 hole(s), 3 wrongly turned edge(s)", or "2 objects have mesh problems: ...") and offers **Repair**; the button is off when only problems remain that repair cannot fix (edges shared by more than two triangles). `RepairMeshCommand` repairs the damaged meshes of the selection on a background thread (`MeshRepair.Repair`; objects that share a mesh, like copies, are repaired once), registers each result under a new id and executes `SetMeshCommand`s as one history entry ("Repair Bad"); undo and redo switch the mesh ids back and forth and the banner follows. The status bar says what was done and what is left ("closed 1 hole(s), turned 1 triangle(s). The mesh is closed and ready."). A before/after overlay (F-REP-04) is not there; undo is.
**Import (`MainViewModel.Import.cs`, F-IMP-01/02, F-FLR-01):** File > Import... (Ctrl+I, `PickImportFiles`, several files) and dropping files on the window (`MainWindow` only forwards the file list to `ImportFilesAsync`). Files are imported one after another (`SemaphoreSlim`, so overlapping imports queue). Per file, on a background task: `MeshImport.LoadAll` (one mesh for STL and OBJ, one per object for 3MF; readable error via `IDialogService.ShowError`, nothing changes), then, for STL and OBJ (a 3MF states its unit, `ImportedMesh.UnitKnown`), if the longest side is below 1 mm or above 1000 mm, the unit question (`PickImportUnit`: millimeters, centimeters, inches; the real dialog is `Views/ImportUnitWindow`, which preselects the unit that gives the most plausible size; cancel skips that file), then `PlaceOnPlate`, a watertight check (skipped above 3 million triangles) and registration in `Meshes`. One object becomes a `MeshNode` named after the file (unique); several objects (3MF) become a `GroupNode` named after the file with one `MeshNode` per object (object names, colors, the arrangement of the file: each child sits at its offset to the common bottom center), added in one `CompositeCommand` (one undo step). The result is placed at the first free spot (`FreeSpot`); the import waits for the evaluation of each file so that the next one sees it; all imported objects are selected at the end and the status bar says how many triangles were read, with a warning when the mesh is not watertight. Unsupported files (for example STEP) are listed in one message and the others are still imported.

`MainViewModel.Meshes` is the one store of the open project: Save writes it into the file (only referenced meshes), Open loads into a fresh store and swaps it in only when the whole file was read, New clears it, autosave and recovery carry it along.

Placement rule (`FreeSpot`): a new shape goes to the first free spot on the X axis (0, -30, +30, -60, ...) so it never hides an existing object; when the row is full up to the edge of the build plate it continues in the next rows (Y = +50, -50, +100, ...), inside the build volume. A shape bigger than the plate takes the first free spot on the X axis. (The spec's F-LIB-04 click or drag placement is not implemented yet.)

Selection: clicking in the viewport selects the clicked object; operands of a Boolean or Merge are selected as the whole node (outermost container). Children of a plain group are selected individually.

**Hole tool (`MainViewModel.Holes.cs`, `HoleToolViewModel`, F-HOL-01, F-HOL-05):** the toolbar button "Drill Hole" (and Edit > Drill Hole, `DrillCommand`) starts a mode that reuses the face pick of F-ROT-04 (`IsPlacingHole`; `IsFacePickActive` is what the viewport binds to; the two modes exclude each other; Esc or the button ends it). A floating panel at the bottom left of the 3D view shows the settings of the next hole (`HoleToolViewModel`: type, diameter, end diameter, head diameter/angle/depth, "Through all", depth; only the fields the type needs are visible; fields accept numbers, expressions and project variables, range errors are shown in the field). A click calls `PlaceHole(FacePick)`: the hole starts at the clicked point (snapped by `SnappedHolePoint`: with "Snap to objects" a click within 15% of the face size (1 to 8 mm) of the face center goes to the center; otherwise, with "Snap to grid", the two directions in the face are rounded to the grid step if the face looks along a world axis and the rounded point is still on the face; Alt or Shift while clicking (`FacePick.NoSnap`), both snaps off or a click that finds no face keep the clicked point; there is no preview marker before the click), its +Z axis is the normal of the clicked triangle, so it stands perpendicular also on a slanted face. A hole cuts the solids of the group it sits in (Q-01), so it joins the nearest group or merge around the clicked part (its local transform is the world placement times the inverse of the parent's), and a body that is not in one is wrapped into a new group together with the hole; this is one `CompositeCommand` ("Drill hole in Group"), so one undo. "Through all" works out the depth when the hole is placed: the extent of the body (the group, if there is one) along the axis plus 1 mm, stored as a plain number (it does not follow later resizing of the body). The cross-section picture (`HoleSection`, pure geometry in picture units, drawn by a `DataTemplate` in `MainWindow.xaml` with the theme brushes) shows the body cut open with the hole in it, in the tool panel (a through hole is drawn 2.5 times as deep as its widest part) and in the properties of a selected hole (`PropertiesViewModel.Section`), where the type is a choice (`HoleType`, one `SetParameterCommand`) and `FieldViewModel.IsVisible` hides the fields the type does not use. The new hole is selected, the tool stays on for the next hole. The hole is then an ordinary object: move and rotate it with the handles (the body is recomputed live), change its parameters in the properties, delete it (F-HOL-05). Locked bodies refuse a hole (message); a pick of something that is not in the scene is ignored.

### 5.9 Projects: save, open, autosave (`Formwerk.IO` and `MainViewModel`)

File format: see [docs/project-format.md](docs/project-format.md). `ProjectFile.Write/Read` work on streams, `SaveAtomic/Load` on paths; reading is defensive and only ever throws `ProjectFormatException` (message for the user). `AutosaveStore` keeps one autosave copy and the information needed to offer recovery.

In the view model:

- **File state:** `FilePath` (null = untitled), `IsDirty`, `WindowTitle` (`name.fwp* - Formwerk`). The project is clean when the undo history is at the position that was saved *and* the command there is the same one (a new edit after an undo replaces the saved branch, so it stays modified). `ReplaceDocument` loads a project: it clears the history (loading cannot be undone), swaps the document content via `FormwerkDocument.ReplaceWith`, and marks the state as saved.
- **Meshes in projects:** `.fwp` files also contain `meshes/<id>.bin` for every imported mesh that an object uses (format in docs/project-format.md); a missing or damaged mesh makes the file unusable instead of silently losing geometry.
- **Commands:** New, Open, Save, Save As (Ctrl+N/O/S/Shift+S). Whenever work would be lost (New, Open, closing) `ConfirmDiscardChanges` asks via `IDialogService`: save, discard or cancel. The window's `Closing` event calls `TryClose`.
- **Autosave:** `AutosaveAsync` (called by a 2 minute `DispatcherTimer` in `App.xaml.cs`) copies the document with `Snapshot()` on the UI thread and writes it on a background thread, only when there is unsaved work. The autosave is deleted when the project is saved, discarded, exited normally, or undone back to the saved state.
- **Recovery:** `OfferRecovery` (called once after the window is shown) finds an autosave left by an unclean exit, asks, and restores it as modified work that belongs to the original file (so Save writes back to it). A damaged autosave is reported and removed.
- **Status messages** ("Saved ...", "Opened ...", "Recovered ...", "Exported ...") stay in the status bar until the next edit (`SetNotice`).
- **`IDialogService`** replaces the earlier file-only interface: save/open pickers, unsaved-changes question, recovery question, error message. The real implementation is `Views/DialogService` (standard Windows dialogs, so the buttons use the system language); tests use `FakeDialogs`.

## 6. Build, test, run

```powershell
.\scripts\build.ps1              # build + test + publish
.\scripts\build.ps1 -SkipTests   # build + publish only
```

The script stops on the first failing step and writes the self-contained program (no .NET install needed, no debug files, English resources only) into the folder `binary` in the root of the repository: `binary\Formwerk.exe`. Copy that whole folder to run the program on another computer. The script refuses to replace the folder while Formwerk runs from it. Test projects run one after another (`-maxcpucount:1`) because the speed tests measure wall-clock time; the whole run takes about 45 seconds. It is run after every work step. For single projects use `dotnet test tests/Formwerk.Tests.Core`.

Requires the .NET 10 SDK (`winget install Microsoft.DotNet.SDK.10`).

Test infrastructure: the tests of the view models are `[UiFact]` (`Tests.App/UiFact.cs`). A `UiFact` runs on a thread of its own with a message pump, like the WPF UI thread: what a view model continues with after background work (`await ... ConfigureAwait(true)`) runs on that thread, one thing at a time, and only when the test waits. xUnit's own context moves such continuations to other threads (measured: the thread changed across an `await`), which let tests race against the view model's own background work and made single tests fail now and then. After the switch: 0 failures in 8 runs of the whole App suite under heavy CPU load (before about 1 in 12 to 25).

Strategy for geometry (spec section 10): invariants (watertight, outward normals), analytic values, property-based tests (FsCheck, planned), golden files, a repair corpus in `testdata/meshes/`, round-trip save/load.

## 8. How to read the code – a suggested path

1. `docs/spec.md` sections 1–3 and 6 (purpose, architecture, data model).
2. `Core/Model/Nodes.cs` – the node types; then `FormwerkDocument.cs`.
3. `Core/Commands/UndoHistory.cs` and `NodeCommands.cs` – how anything changes.
4. `Core/Expressions/` – how typed values become numbers.

## 10. Decisions and open points

- ADR 0001 – Geometry kernel: Manifold, OpenCascade optional later (`docs/adr/0001-geometry-kernel.md`).
- ADR 0002 – UI framework: WPF, viewport via `D3DImage` (`docs/adr/0002-ui-framework.md`).
- ADR 0003 – Kernel implementation: ManifoldSharp (managed Manifold port) in `Formwerk.Kernel` instead of a native P/Invoke binding (`docs/adr/0003-manifoldsharp-kernel.md`).
- ADR 0004 – WPF shell, MVVM toolkit and the interim WPF-3D viewport (`docs/adr/0004-wpf-shell-and-interim-viewport.md`).
- Project file format: `docs/project-format.md` (no new dependency: System.IO.Compression and System.Text.Json are part of .NET).
- ADR 0005 – No GPU renderer for now (decision D-03): the viewport stays on WPF 3D, drag and memory are optimised instead; spec requirements N-PRF-01 and N-GPU-01..04, 06 are postponed (`docs/adr/0005-no-gpu-renderer-for-now.md`).
- Open: Q-01 group/hole semantics, Q-02 group scale, Q-03 boolean speed; see `docs/open-questions.md`.
- Known limit: ungrouping with a non-uniform group scale and a rotated child is approximated (cannot be stored as position/rotation/scale).
- The project is **not under version control yet**; no git commands are run until requested.
